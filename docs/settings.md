# Settings

Set these in `environment` in `docker-compose.yml`. Durations use ISO-8601, for example `PT12H`.

| Variable | Default | What it does |
|---|---|---|
| `CLIENT_PORT` | `8081` | The port of the web dashboard. Change the `ports` mapping to match. |
| `CLIENT_PICKUP_INTERVAL` | `PT12H` | How often the newest archive is downloaded automatically. Between 1 second and 365 days; a value outside that range is ignored with a warning and the default is used. Only the initial value: once it is saved in the dashboard, the stored value is used. The time of the last successful pickup is kept in the state file, so a restart does not reset the schedule: a pickup that is overdue runs on the first check (every minute) once the client has an active server, a stored pairing, and the server answers; otherwise it runs at the original due time. A pickup that cannot run is retried after 1, 2, 5, 10 and then every 15 minutes. After a successful automatic pickup, the earlier `*-media-backup-AD.zip` copies of the older archives the active server still lists are deleted from the download directory; newer copies, copies of archives the server no longer lists (such as those from another server) and all other files are kept. Downloading the latest archive by hand also counts as a pickup. Switching to a different active server clears the last pickup time, so the first pickup from the new server is due at once; a download that was started from the old server and finishes after the switch does not set the new server's pickup time. Incomplete `.part` files left in the download directory by a crash are deleted on startup and before each pickup, except those of a transfer in progress. If the time of a pickup cannot be saved, the client retries on the same backoff. |
| `CLIENT_BACKUP_RUN_TIMEOUT` | `PT6H` | How long "Run Backup Now" waits for the server to finish. Minimum `PT1M`. If a run takes longer, the dashboard shows an error, but the backup keeps running on the server. |
| `MEDIAGARRD_SERVER_IP` | (none) | A server to connect to automatically, as `<ip>`, `<ip>:<port>` or `https://<host>[:<port>]`. See [network.md](./network.md). |
| `MEDIAGARRD_SERVER_CA` | (none) | A PEM file with extra certificate authorities (or a self-signed certificate) to trust for connections to the server, in addition to the system ones. The client refuses to start if the file cannot be read. See [https.md](./https.md). |
| `CLIENT_PASSWORD` | (none) | The dashboard password. When set it overrides any stored password and the set-password form is disabled. |
| `CLIENT_RESET_PASSWORD` | `false` | `true` removes the stored dashboard password on start, so the first visitor can set a new one. Remove it again afterwards: while it stays set, every restart reopens that window. |
| `MEDIAGARRD_SERVER_PORT` | `38471` | The server port tried first by "Scan Local Network" and "Connect by IP". |
| `MEDIAGARRD_UPDATE_REPOSITORY` | `MediaGarrd/Client` | The GitHub repository checked for new releases. |
| `MEDIAGARRD_GITHUB_API_URL` | `https://api.github.com` | The GitHub API used for the release check. |
| `MEDIAGARRD_UPDATE_CHECK_INTERVAL` | `PT24H` | How often the release check runs. Minimum `PT1H`. |
| `CLIENT_STATE_FILE` | `/var/lib/mediagarrd/client/state.json` | Where the client keeps its selected server, known servers, pickup interval, the time of the last pickup and the tokens of its paired servers, inside the container. The file is readable by its owner only. The dashboard password hash is stored next to it as `password.json`. |
| `CLIENT_DOWNLOAD_DIRECTORY` | `/var/lib/mediagarrd/downloads` | Where downloaded archives are saved, inside the container. Archives are written with owner-only permissions (`0600`) and directories the client creates are `0700`; an existing directory is left as it is. |

The container starts as root only to hand the two data folders and the client's own files in them to UID 1000, then runs the client as that user. Set `PUID` and `PGID` in `environment` to use another owner, for example your own user on the host (`id -u`, `id -g`). Only the folders themselves and the client's own files are changed: the state file and its copies, `password.json`, and `*-media-backup.zip`, `*-media-backup-AD.zip` and their `.part` files. Other files in those folders, and the subfolders, are not touched. With `PUID=0` the client keeps running as root. If you set `user:` in Compose, nothing is changed and the folders must already belong to that user.

Because Java no longer runs as root, two settings need care. With `network_mode: host` keep `CLIENT_PORT` at 1024 or above, since a non-root process cannot bind a lower port. With `cap_drop: ALL` add back `CHOWN`, `SETUID` and `SETGID` (the entrypoint needs them to hand over the folders and drop to UID 1000), or run with `user:` instead. If the state file exists but this user cannot read it, the client refuses to start and names the file and the UID, instead of moving it aside; fix its owner or permissions.

To change where data is kept on the host, change the left side of the volumes in `docker-compose.yml`:
- `./data/client/downloads`: downloaded archives.
- `./data/client/state`: the client's state. Keep it on persistent storage.

## Failure webhook
The dashboard's Server Configuration view has a Failure Notifications panel for the connected server's optional failure webhook: a URL the server posts to when a backup fails or only partly succeeds (see the server's settings page for the message formats). Enter a URL and press Save Webhook, press Clear to turn it off, or Send Test to have the server post a test message now (if a URL is typed in the field it is saved first). The panel shows `Configured: https://host` and never the saved URL, because Discord and Slack webhook URLs are secrets; to change it, type the new one. Send Test is limited to one every 10 seconds. The URL is stored on the server, not in the client's state file.

## Dashboard login
Opening the dashboard asks for a password. If none is set yet, whoever opens it first chooses one (at least 8 characters). Set `CLIENT_PASSWORD` to choose it yourself instead. The password is stored as a salted PBKDF2-HMAC-SHA256 hash in `password.json` next to the state file; keep that directory on persistent storage and private.
- Sessions end after 12 hours without activity or 7 days in total, and when the client restarts.
- Only one login attempt per address is checked at a time and only a few are checked at once overall; extra attempts get 429.
- Password checks from all addresses together share a budget of 30 a minute. A successful login gives its check back. When the budget is used up, logins get 429 with a `Retry-After` of a few seconds and no password is checked, and nobody is locked out for a fixed time. Someone who sends requests from many addresses can still use up the budget and make the owner wait for the next free check; set `CLIENT_PASSWORD` to a long random value and keep the dashboard behind a VPN or reverse proxy that limits access.
- After the 4th failed login from one address, further attempts from it are refused with a delay that grows from 5 seconds to 5 minutes. Behind a reverse proxy every visitor shares the proxy's address, so the delay applies to all of them.
- Forgot the password? Start once with `CLIENT_RESET_PASSWORD=true`, open the dashboard, set a new one, then remove the variable.

## Pairing
A client must be paired with each server it uses. Choose the server in the dashboard and enter the `Pairing PIN` that the server's setup page shows after Finish Setup (it is also in the server's logs), or a pairing code from a client that is already paired. The client stores the token as soon as the server issues it and then confirms the pairing with one request. It discards the token only when the server refuses the confirmation, so after that error you can enter the same PIN or code again. If the confirmation cannot be completed (the server is unreachable or answers with an error), the client keeps the token and says so: the server confirms it on the client's next connection, which happens within seconds. If the server never received a request with it, the unconfirmed pairing expires after 5 minutes, the client then asks you to pair again, and the same PIN (or a new pairing code) works. A client that is already paired with a working token refuses to pair again (`409`); unpair it first. The token is kept in the state file per server address and is never shown. Tokens are tied to the exact address: `http://<ip>:38471` and `https://garrd.example.com` need separate pairings.
